DISCOUNTS ARCHITECTURE — how codes get onto diski.nl
====================================================
Last updated: 2026-09-01 (shops.json added; the dummy/backup-code sections rewritten
— they described mechanisms that no longer exist)

!! USE NODE 22. Your shell's default node is too old — the pipeline will die with
!! "process.loadEnvFile is not a function". Both repos:
!!     source ~/.nvm/nvm.sh && nvm use 22
!! light19's build has always needed it; run-all.js needs it now too, because it
!! fetches over the network.

(The counts in this document — 2774 codes, 897 newsletter rows, 1230 pages — are
whatever they happened to be on the day it was written. They move every run. Don't
treat them as targets.)


THE ONE-PARAGRAPH VERSION
-------------------------
Discount codes live in Cloudflare R2. They are published there by the
diski-input-insta repo, and read from there by two consumers: the diski app (at
runtime) and light19 (at build time). light19 turns that feed into
src/app/data/discounts.json, topping it up with a NEWSLETTER ROW for any shop that
has earned a page but has no live code. Every part of the website reads that one
file. A page exists on diski.nl if, and only if, it has an entry in it.

light19 also PUBLISHES one feed of its own: shops.json, the list of shops that have
a page. That exists for the app, which cannot work that list out for itself.

THE PIPELINE, END TO END
------------------------

  [diski-input-insta]  (private, the master data)
      src/assets/discounts.json          <- YOU EDIT THIS. Column 4 = influencer handle.
             |
             |  node scripts/run-all.js          (NODE 22, asks for confirmation)
             |    publish-discounts-to-r2.js — parses the master, applies the code
             |    allowlist, puts our own code on top per shop, uploads. That is the
             |    whole job: the dummy-code and anonymize steps are GONE (see below).
             v
  [Cloudflare R2]  bucket "promotions"
      discounts.json   <- codes, published by diski-input-insta
      shops.json       <- pages, published by LIGHT19 (this repo)
      https://pub-a3be569620e4415b916e737210363aee.r2.dev/<key>
             |
             +---------------------------+
             |                           |
             v                           v
  [diski app]                   [light19]  npm run build:prod

THE PUBLISHED FEEDS (what's in R2)
----------------------------------
discounts.json — real codes only. 2774 rows across 767 shops.
  {
    "generated": "2026-09-01T09:10:44.426Z",
    "count": 2774,
    "discounts": [
      { "shop": "loavies", "code": "LOTTE20", "value": "20", "added": "2026-07-10" },
      { "shop": "footlocker", "code": "FL10", "value": "10", "added": "2026-07-08",
        "condition": "new app user" }
    ]
  }

shops.json — which shops have a page, and why. 1230 rows.
  {
    "generated": "2026-09-01T09:43:39.804Z",
    "count": 1230,
    "shops": [
      { "shop": "hunkemoller", "affiliate": "https://tidd.ly/4j17AXp", "page": "v2" },
      { "shop": "volero.nl", "page": "v1" }
    ]
  }

Clean objects. No influencer handles. `shop` is the lowercased slug in both — the
join key every consumer uses.

SAFETY (codes): the published schema simply has no field for the influencer handle.
parseLine reads columns 1, 2, 3 and 5 and drops the rest, so no handle can reach R2
by construction. The old anonymize step and its guard were removed once the payload
was verified byte-identical with and without them.


ONE FALLBACK: NEWSLETTER ROWS
-----------------------------
A shop that has earned a page but has no live code gets one row in discounts.json:

    hunkemoller, aanmelden voor nieuwsbrief, 10, zzz, 08-25

The modal matches that exact string (modal.component.ts, NEWSLETTER_CODE), drops the
whole code block — there is nothing to copy, reveal or share — and says what to do
instead, keeping the "Naar winkel" button on the affiliate link. Two things earn a
page: an affiliate link, or brand content (v1 or v2). 897 rows today.

THERE USED TO BE TWO INVENTED FALLBACKS, and they are both gone. diski-input-insta
filled a "dummy code" for affiliate partners with none; each brand page carried a
"backupCode" (its last real code, an archived one, or — for ~89 shops — a code
synthesised out of {ACTIE,OFF,SHOP} x {10,15}). Both reached the site as ordinary
codes, so a visitor could not tell an invented code from a real one, and neither
could we. The guarantee they provided was right; inventing a discount to provide it
was not. With them went add-dummy-codes.js, the dummyCode fields, backup-codes.json,
and the hardcoded cross-repo eval() of affiliate-link.service.ts by absolute path —
which was the most fragile joint in the whole pipeline.

THE DATE ON A NEWSLETTER ROW — the build date minus 7 days, one shared date for all
of them. A sign-up doesn't expire, so the date could honestly be the build date, but
two consumers read recency as a signal and both would misread it:
  1. The homepage counts every shop carrying the NEWEST date as a "nieuwe shop".
     Build-dated rows would announce ~897 new shops on every build.
  2. The modal's email gate demands an email for anything added in the last 5 days.
     A row with no code must never sit behind that.
A week clears both, and cannot collide: codes reach the feed every two to three days.


SHOPS.JSON — THE FEED THIS REPO PUBLISHES
-----------------------------------------
scripts/publish-shops-to-r2.js, step 3 of build:prod. Both it and fetch-discounts.js
read the set from scripts/shop-universe.js, which is the single definition of "what
earns a page" — two copies of that logic would drift.

WHY IT EXISTS. The app reads the codes feed, so it saw 767 shops while the site had
1230 pages. It cannot compute the difference: 414 of those shops have brand content
and no affiliate link, and both facts live only in this repo. Those shops did not
exist in the app at all — not in search, not in the shop list, and not in the follow
manager, which is exactly where a shop that has nothing right now is worth following.

IT CARRIES FACTS, NOT COPY. No newsletter text, no 10%. That is this site's answer to
"no code"; the app gives a different one (the newsletter CTA behind the affiliate
click-out where there is a link to fire, a follow where there isn't). Publishing the
row shape instead would put `aanmelden voor nieuwsbrief, 10` in a feed where a naive
consumer renders it as "10% korting" for a shop with no offer — the exact trap the
dummy and backup codes fell into.

IT IS ALSO THE AFFILIATE FEED. Every row carries the link, which retires the app's
INFRA-2 stopgap: it used to regex affiliate-link.service.ts off raw.githubusercontent
on branch `new_diski_look`, and a branch rename would have silently unmonetised every
tap in a released build.

CREDENTIALS. light19/.env needs R2_ACCOUNT_ID / R2_ACCESS_KEY / R2_SECRET_KEY — the
same three diski-input-insta uses. THIS IS THE FIRST THING IN THIS REPO THAT WRITES
to the bucket; everything else only reads it.

NON-FATAL BY DESIGN. Missing credentials or a failed upload warn and the build
continues. The website does not read this feed — it reads its own generated
discounts.json — so failing a site build over an app feed would be the wrong trade.
The one thing that DOES fail the build is shop-universe.js not being able to parse
the affiliate service or the content dirs, because fetch-discounts.js reads the same
set and the site is then about to be wrong too.


PAGE EXISTENCE — ONE RULE
-------------------------
    A page exists if it has an entry in discounts.json. That's the whole rule.

scripts/fill-routes.js builds routes.txt and sitemap.xml straight from that file.
It used to compute a three-way union (discounts ∪ v1 content ∪ v2 content), because
back then a pruned shop's code was applied inside the component and discounts.json
never learned the shop existed. Now that newsletter rows are injected into the file
itself, every content page has an entry there by construction, and the union
collapsed to its first term.

fill-routes.js still reads the v2 content directory — but only to answer a DIFFERENT
question: which COMPONENT renders a slug (v2 vs v1). It generates
brand-content/v2-content-slugs.ts, the manifest the router guard reads. Having a
data/{slug}.json file IS being live on v2.

THE GUARD. That rule is now load-bearing: a content page missing from discounts.json
would simply not exist — no route, no page, silently. So fetch-discounts.js FAILS THE
BUILD, naming the shop, if any v1 or v2 brand page ends up with neither a live code
nor a newsletter row. That should be impossible — the fallback covers every content
slug by construction — so the guard is there to keep it structural rather than
assumed. (Before, the union would have quietly kept such a page online.)


WHO READS discounts.json
------------------------
  discounts-table.component.ts   the homepage code table, search, "X nieuwe shops"
  winkels.component.ts           the /winkels shop directory
  company-codes.component.ts     v1 brand pages
  company-codes-v2.component.ts  v2 brand pages
  fill-routes.js                 routes.txt + sitemap.xml (at build time)

The service (services/discounts.service.ts) statically imports the file, so it is
BUNDLED, not fetched at runtime. That is deliberate: the codes must be in the
prerendered HTML or Google never sees them.

THIS IS WHY THE FALLBACK IS INJECTED INTO THE DATA RATHER THAN APPLIED IN A
COMPONENT. They used to be applied inside the two brand-page components, at render
time. The page got its code — but discounts.json never learned the shop existed, so
the homepage table, /winkels, the search, and other pages' related-shops grids all
behaved as if it didn't. 275 shops were online, with a working code, and unfindable.
Moving the fallback from the view into the data fixed all of them at once, deleted
both component fallbacks, and dropped the v1 backup map out of the client bundle
(initial bundle 1.01 MB -> 989 kB, because the browser no longer downloads 578 backup
codes it will never use).


BUILD ORDER (npm run build:prod)
--------------------------------
  1. stamp-build.js          writes BUILD_DATE_ISO into src/app/build-info.ts
                             MUST be first — fetch-discounts.js needs it to date
                             newsletter rows, and the pages stamp themselves with it.
  2. fetch-discounts.js      R2 codes feed + injected newsletter rows -> discounts.json
                             MUST be before fill-routes.js, which reads that file.
  3. publish-shops-to-r2.js  uploads shops.json for the app. Reads nothing the later
                             steps write, so its position is not load-bearing — but it
                             sits next to fetch-discounts.js because they share
                             shop-universe.js. Never fatal.
  4. fill-routes.js          routes.txt, sitemap.xml, v2-content-slugs.ts
  5. generate-spotted-sales.js
  6. generate-shop-urls.js
  7. ng build --configuration production   (prerenders ~1499 routes)
  8. set-canonicals.js


DAY-TO-DAY: HOW DO I ...
------------------------
ADD OR CHANGE A CODE
  Edit diski-input-insta/src/assets/discounts.json, then:
      cd diski-input-insta && node scripts/run-all.js
  It asks for confirmation, applies the code allowlist, puts our own code on top per
  shop, and publishes to R2. The app sees it immediately. The website sees it on its
  next build.

  Dry run (does everything except the upload):
      node scripts/run-all.js --dry-run

  The R2 credentials load from diski-input-insta/.env automatically — nothing to
  remember, no flags.

REFRESH CODES FOR LOCAL DEV
  `ng serve` does NOT fetch from R2 — it just uses whatever discounts.json is on
  disk. To pull fresh data first:
      node scripts/fetch-discounts.js && npm start

PUBLISH SHOPS.JSON WITHOUT A FULL BUILD
      node scripts/publish-shops-to-r2.js
      node scripts/publish-shops-to-r2.js --dry-run
      node scripts/publish-shops-to-r2.js --dry-run --out /tmp/shops.json
  Needs R2_ACCOUNT_ID / R2_ACCESS_KEY / R2_SECRET_KEY in light19/.env. Without them
  it prints the counts, warns, and exits 0.

ADD A NEW V2 BRAND PAGE
  Drop a data/{slug}.json file in. It goes live on v2 automatically, and it gets a
  newsletter row on the next build if the shop has no live code — no backupCode field
  to fill in any more.

THE BUILD FAILED WITH "brand page(s) got no row in discounts.json"
  The fallback loop has a hole — every content slug should get a row by construction.
  Check scripts/shop-universe.js against the content directories; the shop named would
  otherwise get no route and vanish from the site.

READ THE OUTPUT OF A RUN
  fetch-discounts.js prints e.g.
      Wrote 3671 discounts: 2774 live + 897 newsletter (covering all 576 v1 + 569 v2)
  Watch the NEWSLETTER number between runs. It going UP means shops lost their last
  live code and fell back (their pages stay, they stay findable). It going DOWN means
  a shop got a real code again and was promoted into the live block.

  publish-shops-to-r2.js prints e.g.
      1230 shops, 74 KB (576 with an affiliate link, 969 with brand content)
  That first number should only move when brand content or the affiliate map changes,
  never when codes come and go — it is a statement about this repo, not about R2.

  routes.txt going DOWN is normal and correct when a CODE-ONLY shop (no v1/v2
  content) loses its last code: there is nothing left to put on a page, so the page
  goes. Those URLs will start 404ing and will show up in Search Console. A shop WITH
  content never disappears — it falls back to a newsletter row instead.


GOTCHAS
-------
- discounts.json in light19 is GENERATED. Do not hand-edit it.
- Codes ship in the JS bundle by design (prerendered HTML needs them for SEO).
  Do not "optimise" this into a runtime fetch.
- The website's codes are only as fresh as its last build. The app's are live.
  If you want the site fresher, trigger a rebuild when R2 is written.
- Publishing must stay the LAST step of run-all.js — it ships whatever the earlier
  steps produced.
- The codes feed contains NO newsletter rows, and shops.json contains NO codes or
  copy. Keep it that way: the moment a placeholder is shaped like a code, a consumer
  renders it as one. That is how the dummy and backup codes went wrong.
- shops.json is only as fresh as the last WEBSITE BUILD. That is fine by
  construction — it describes what the website has — but it means a brand page added
  today reaches the app on the next deploy, not immediately.
